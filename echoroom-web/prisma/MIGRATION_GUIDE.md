# EchoRoom — Prisma Migration Guide

## Conventions for Safe Migrations

### 1. Always Create a Down Migration

Every `migration.sql` generated by Prisma must be accompanied by a **companion `.down.sql`** file with the inverse SQL operations. This enables automated rollback via `prisma/rollback.ts`.

**File naming:**
```
prisma/migrations/
├── 20260531163244_sprint2_columns_and_types/
│   ├── migration.sql          # Prisma-generated
│   └── migration.down.sql     # Manual — inverse SQL
├── 20260531163245_sprint2_indexes/
│   ├── migration.sql
│   └── migration.down.sql
└── ...
```

**What a `.down.sql` should contain:**

- `DROP TABLE` for each created table (in reverse dependency order)
- `DROP INDEX` for each created index
- `ALTER TABLE ... DROP COLUMN` for each added column
- `ALTER TABLE ... ADD COLUMN` for each dropped column
- `ALTER TYPE ... DROP VALUE` — Only if PostgreSQL allows it (PG 14+). Otherwise, document the constraint.

**Example `migration.down.sql`:**
```sql
-- Rollback: 20260531163244_sprint2_columns_and_types
DROP INDEX IF EXISTS "UserSocial_totalLikesReceived_idx";
DROP INDEX IF EXISTS "UserSocial_totalCallsMade_idx";
DROP TABLE IF EXISTS "UserBilling";
DROP TABLE IF EXISTS "UserSocial";
DROP TABLE IF EXISTS "UserProfile";
```

### 2. Migration Workflow

#### Creating a new migration (standard):

```bash
# 1. Edit schema.prisma
# 2. Generate the migration
npx prisma migrate dev --name my_migration_name

# 3. Manually create the down migration
# Copy the generated migration.sql and write inverse operations
touch prisma/migrations/$(ls -t prisma/migrations | head -1)/migration.down.sql

# 4. Review both files before committing
```

#### Applying migrations in production:

```bash
npx prisma migrate deploy
```

> ⚠️ Never use `prisma migrate dev` in production — it resets the database.

#### Rolling back migrations:

```bash
# Rollback the last 2 migrations
npx tsx prisma/rollback.ts --step 2

# Rollback to a specific migration (20260531163244 becomes current)
npx tsx prisma/rollback.ts --to 20260531163244

# Force rollback in production (requires confirmation without --force)
NODE_ENV=production npx tsx prisma/rollback.ts --step 1 --force
```

### 3. Migration Safety Rules

| Rule | Reason |
|------|--------|
| **Never edit applied migrations** | `_prisma_migrations` checksums will mismatch; Prisma CLI will refuse to proceed |
| **Always test down migrations** | Apply the migration, roll it back, verify the schema matches |
| **Additive changes are safest** | Adding columns/tables is easy to roll back; removing columns and data-migration is high-risk |
| **Avoid renaming columns** | Use a 3-phase approach: add new column → migrate data → drop old column |
| **Wrap data migrations in transactions** | If a data transformation fails mid-way, the transaction isolates side effects |
| **Back up production before any migration** | Use Aiven backups or `pg_dump` |
| **Run rollbacks during low-traffic windows** | Rolling back DDL can hold `ACCESS EXCLUSIVE` locks |

### 4. Unsafe Operations

The following operations are **dangerous in production** if not carefully planned:

- `ALTER TABLE ... DROP COLUMN` — Irreversible if the column has data (you need a backup)
- `ALTER TYPE ... DROP VALUE` — May fail if the value is in use; silently corrupts existing rows in older PG
- `DROP TABLE` — Destructive; ensure no data loss
- Column renames (`RENAME COLUMN`) — Breaks queries mid-deploy; use add + migrate + drop pattern
- `CREATE INDEX CONCURRENTLY` — Breaks transaction semantics but avoids locks; use carefully
- Adding `NOT NULL` to a populated column — Requires a CHECK or a multi-step migration

### 5. The 3-Phase Migration Pattern

For destructive changes (column drops, renames, type changes):

**Phase 1 — Additive (non-breaking):**
- Add new columns, tables, or indexes
- Write to both old and new columns
- Deploy application code that reads from the new column

**Phase 2 — Migration (background):**
- Run a data migration script to backfill old data into new columns
- Verify data integrity

**Phase 3 — Cleanup (breaking):**
- Remove old columns/tables
- Deploy rollback-agnostic code
- Create `.down.sql` for Phase 3 operations

### 6. Checking Migration Status

```bash
# Via Prisma CLI (requires valid DATABASE_URL)
npx prisma migrate status

# Via SQL (direct query)
psql "$DATABASE_URL" -c "SELECT migration_name, finished_at FROM _prisma_migrations WHERE rolled_back_at IS NULL ORDER BY finished_at;"
```

### 7. Regenerating the Prisma Client

After any migration (apply or rollback), regenerate the client:

```bash
npx prisma generate
```

This ensures the TypeScript types match the current database schema.
